# Testing strategy

Tests are written from acceptance criteria before the implementation
([ADR-0001](../adr/0001-spec-driven-development-and-adrs.md#adr0001-spec-before-code-v1))
and cite the requirement they verify
([ADR-0005](../adr/0005-versioned-requirement-anchors.md#adr0005-tests-cite-requirements-v1)).

## Levels

| Level | What | Tools | Runs |
|---|---|---|---|
| Unit | one module through its interface, dependencies faked (`FactQuery` fake for `verify`) | GoogleTest | every preset, every change |
| Handoff | golden bundles for fixtures; recorded agent outputs (valid and broken) for `ingest` | GoogleTest + committed test data | every change |
| Analysis fixtures | `analysis` on tiny C/C++ projects under `tests/fixtures/` with hand-written expected facts | GoogleTest + fixture `compile_commands.json` | every change |
| Golden files | fact export, module map, report: byte-for-byte against committed files | GoogleTest | every change |
| Determinism | same input, 1 vs N threads, shuffled TU order → identical export ([NFR-004](../specs/requirements.md#nfr004-deterministic-output-v1)) | GoogleTest | every change |
| Architecture | deterministic core does not link `llm` | CMake configure check | every configure |
| Fuzzing | parsers of untrusted input | libFuzzer + ASan/UBSan | 60 s per change in CI; longer runs locally |
| End-to-end | CLI on libmodbus: analyze → map (M1); → handoff → ingest of a recorded agent output → report (M2) | shell script, CTest | CI |
| Verifier accuracy | labelled claim set (below) | GoogleTest data-driven | every change from M2 |

All tests also run under ASan + UBSan (`asan-ubsan` preset).

### <a id="testing-fixture-rules-v1"></a>Fixture rules

- Each fixture is a minimal project for one concern: `two_modules` (includes,
  module deps), `static_same_name` (two `static` functions with one name),
  `fn_pointers` (direct vs indirect calls, a backend table like libmodbus),
  `macros` (calls inside macros), `broken_tu` (one TU that does not parse).
- Expected facts are written by hand, not copied from tool output. A golden
  file is only regenerated by a human who reviews the diff.

## <a id="testing-characterization-v1"></a>Characterization tests (libmodbus)

Goal: pin the current behaviour of libmodbus's frame handling before
building a wrapper on top of it (M3, then M5).

- Start from skeletons generated by `lcart testgen`
  ([FR-016](../specs/requirements.md#fr016-characterization-test-skeleton-v1)), fill in
  observed values by running the code, as in *Working Effectively with
  Legacy Code*: the test asserts what the code **does**, including
  surprising behaviour. Surprises are written down as findings, not "fixed"
  in the test.
- Test through the public API where possible. Internal functions such as
  `_modbus_receive_msg` (in `src/modbus.c` at v3.2.0) are reached through a
  backend; feeding bytes needs a seam (a socketpair for TCP, or a pty for
  RTU). TODO: verify which seam is least invasive without modifying
  libmodbus ([open questions](../open-questions.md)).
- Tests live in `tests/targets/libmodbus/` (outside the submodule) and link
  the unmodified library.

## <a id="testing-fuzzing-v1"></a>Fuzzing

| Target | Input | Milestone |
|---|---|---|
| `claim_json_fuzzer` | arbitrary bytes as agent output → `parse_claims` | M2 (stub exists) |
| `project_config_fuzzer` | arbitrary bytes as `lcart.toml` → `parse_project_config`, then every accepted glob matched | M1 (B-11, runs in CI) |
| libmodbus frame parsing | arbitrary bytes as a received frame through the seam above | M4 |

- Sanitizers: ASan + UBSan. Corpora are kept out of the repository except a
  small seed set; crashes become regression tests.
- AFL++ for libmodbus is optional (M4): it adds value with a different
  mutation strategy only once libFuzzer coverage plateaus.

## <a id="testing-verifier-accuracy-v1"></a>Measuring the verifier's accuracy

The verifier is the product's core promise, so it is measured like a
classifier, independently of any LLM.

**Labelled claim set.** `tests/claims/labelled/*.json`: claims with the
expected status, written by a human from reading the code (not from the fact
database). Sources:

1. **True claims** sampled from the fixtures and from libmodbus, checked by
   reading the code.
2. **Mutated false claims**, generated from true ones and then reviewed:
   swap callee for a function that exists but is not called; reverse an
   include; negate; invent a plausible name (`modbus_rtu_check_crc`-style);
   attribute a `static` function to the wrong file.
3. **Hard cases** expected to be `unverified`: calls through the backend
   table, calls only inside `#ifdef` branches not compiled with the given
   flags, functions in TUs that failed to parse.
4. **Real agent claims** (from M2): claims produced by the agents and models
   used, labelled by hand. These show which mistakes models actually make.

**Metrics** (per claim kind and overall), from the confusion matrix of
expected vs actual status:

- **Precision of `confirmed`** (target ≥ 0.99): a false confirmation lends
  authority to a wrong statement, the most harmful error.
- **Precision of `contradicted`** (target ≥ 0.95): false alarms waste review
  time and erode trust.
- **Recall of `contradicted`** on false claims: how many wrong statements are
  caught rather than left `unverified`. Reported, no hard target in v1.
- **Unverified rate**: how often the tool cannot decide; tracked over time.

These targets are [NFR-009](../specs/requirements.md#nfr009-verifier-accuracy-measured-v1).
CI fails below the targets. The labelled set grows with every bug found in
the verifier.

**Not measured here:** how often LLMs are wrong. That is a property of the
model; the report's per-status counts for real runs show it, and a table per
model is kept in the libmodbus case study.
