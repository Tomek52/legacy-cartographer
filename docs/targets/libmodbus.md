# Target: libmodbus

## Why libmodbus

- Real, long-maintained C code, small enough to
  understand fully: about 5.8 kLOC of `.c` and `.h` in `src/` at v3.2.0
  (`wc -l`).
- It parses an industrial protocol from the network and serial lines, which
  makes frame parsing a meaningful target for characterization tests and
  fuzzing.
- Its structure has a feature that tests the analysis honestly: transport
  backends (RTU, TCP) are reached through a table of function pointers
  (`struct _modbus_backend` in `src/modbus-private.h`, with members such as
  `recv` and `check_integrity`), so many calls are indirect
  ([FR-015](../specs/requirements.md#fr015-resolve-function-pointer-tables-v1)).
- Licence LGPL-2.1-or-later; obligations in
  [ADR-0003](../adr/0003-licensing.md).

## Module configuration

All library sources are in `src/`, so the default directory-based module
rule would give one module. The libmodbus configuration (B-14) defines:

| Module | Files |
|---|---|
| `core` | `src/modbus.c`, `src/modbus-data.c`, `src/modbus.h`, `src/modbus-private.h`, `src/modbus-version.h` (generated by configure) |
| `rtu` | `src/modbus-rtu*` |
| `tcp` | `src/modbus-tcp*` |
| `tests` | `tests/*` |

## Plan by milestone

### M1: fact database and module map (no LLM)

1. Generate `compile_commands.json` outside the submodule:
   `scripts/libmodbus-compdb.sh` (B-05). `autogen.sh` writes its generated
   files (`configure`, `Makefile.in`, ...) into the source directory, so an
   out-of-tree `../configure` alone would still modify the submodule. The
   script therefore exports the pinned commit with `git archive` to
   `build/targets/libmodbus/source/`, runs `autogen.sh`, `./configure
   --enable-tests` and `make` there under `bear`, and writes
   `build/targets/libmodbus/compile_commands.json` (14 translation units:
   the 4 library sources and 10 programs in `tests/`). That copy is the
   analysis root: it holds the pinned files unchanged plus what configure
   generates (`config.h`, `src/modbus-version.h`, `tests/unit-test.h`), so
   the generated header belongs to `core` as the table above says.
2. `scripts/libmodbus-baseline.sh` (B-14) runs step 1, then `lcart
   analyze` and `lcart map` with `scripts/libmodbus/lcart.toml`, the module
   configuration above. `config.h`, generated at the root of the copy,
   falls into the default `(root)` module.
3. The script checks that `modbus.c` defines `_modbus_receive_msg`,
   `modbus_receive`, `compute_meta_length_after_function`,
   `compute_data_length_after_meta`, `check_confirmation` and
   `modbus_reply`, `modbus-rtu.c` defines `crc16` and
   `_modbus_rtu_check_integrity`, and `modbus-tcp.c` defines
   `_modbus_tcp_check_integrity` (all seen in v3.2.0); that
   `_modbus_receive_msg` calls `backend.recv` and `backend.check_integrity`
   indirectly; and that `core` has no direct call into `rtu` or `tcp` (its
   dependencies on them are include edges: `modbus.h` includes both
   backend headers).
4. The generated [module map](libmodbus-map.md) is committed; the CI job
   `libmodbus baseline` regenerates it with no network and fails if it
   changes.

**Baseline (NFR-005).** `lcart analyze`
on the 14 translation units: **1.12 s** with a Release build in the CI job
`libmodbus baseline` (GitHub-hosted `ubuntu-24.04` runner, first run
2026-10-04), the reference; 1.6 s with a debug build on the 4-core
development container. The job prints the time on every run. Budget: 60 s
([NFR-005](../specs/requirements.md#nfr005-performance-budget-v2)).

**Hand check (B-23, 2026-10-09).** Each function of step 3 was compared
with the source of the pinned tag (`a9b025d`), read by hand in the copy that
`scripts/libmodbus-compdb.sh` builds: its definition (file and line range,
from `lcart query export`) and every call written in its body (from `lcart
query callees`). Calls of functions outside the root (`printf`, `memcpy`,
`FD_SET`, ...) are not edges by design
([data model](../architecture/data-model.md#arch-data-model-call-edges-v1)).

The source of `_modbus_receive_msg` spells `modbus_close` and
`modbus_connect` four times each: two pairs are in `#ifdef _WIN32`
branches, which the Linux build does not compile, so two calls each are
right. Names in comments and string literals of `modbus_reply`
(`modbus_receive`, `write_bits`, `write_registers`) are not calls. Which
backend functions the indirect calls reach is FR-015 (M2).

### M2: generated documentation and verification report

1. `lcart handoff` for libmodbus, then run a coding agent (Claude Code) on
   the bundle with the prompt from the [handoff contract](../specs/handoff-contract.md).
   Run it twice: facts-only, and with `--include-source` (libmodbus is
   public, so sharing excerpts is fine), and compare the verification
   reports.
2. Publish the docs with their verification reports. Contradicted claims are
   kept and shown: they are the point of the demonstration.
3. Label the real claims and add them to the verifier's labelled set.

### M3: characterization tests of frame handling

Target behaviour (exact functions TODO: verify while writing the tests):

- request parsing on the server side: `modbus_receive` → `_modbus_receive_msg`
  → length computation (`compute_meta_length_after_function`,
  `compute_data_length_after_meta`) → backend integrity check (CRC for RTU,
  MBAP header checks for TCP);
- response handling on the client side: `check_confirmation`;
- `modbus_reply` for each supported function code, including exception
  responses and the length validation added in v3.2.0 (per upstream
  `NEWS.md`).

Seam: feed bytes through a real transport without changing libmodbus, e.g. a
TCP context connected to a socketpair or loopback socket, or an RTU context
on a pseudo-terminal. TODO: verify which works with the public API only.

### M4: fuzzing

- libFuzzer harness that delivers one fuzzed frame per iteration through the
  seam from M3 into the server-side receive path and `modbus_reply` with a
  mapping from `modbus_mapping_new` (TODO: verify signature and teardown
  cost per iteration).
- Built with ASan + UBSan, linking an instrumented build of the unmodified
  libmodbus sources (compiled by our CMake from the submodule's files; no
  changes to them).
- AFL++ optional, once libFuzzer coverage plateaus.
- Findings are reported upstream following its `SECURITY.md`, not fixed
  here.

### M5: modern C++20 wrapper

The wrapper's public API stays C++20 for its users ([ADR-0007](../adr/0007-cpp23-and-toolchain-baseline.md#adr0007-wrapper-stays-cpp20-v1)).

- Header + small library in `wrappers/modbus-cpp/` (outside the submodule):
  RAII context (`std::unique_ptr` with a custom deleter calling
  `modbus_free`; TODO: verify close/free semantics), `std::span` for
  buffers, `std::chrono` for timeouts, error codes mapped from `errno` /
  `modbus_strerror` into a `Result` type, no exceptions across the C
  boundary.
- Tests: the M3 characterization tests rerun through the wrapper must give
  the same results; plus unit tests of the error mapping.
- Licensing: dynamic linking by default and the other obligations in
  [ADR-0003](../adr/0003-licensing.md#adr0003-lgpl-wrapper-obligations-v1).
