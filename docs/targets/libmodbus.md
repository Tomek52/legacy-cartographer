# Target: libmodbus

## Why libmodbus

- Real, long-maintained C code, small enough to
  understand fully: about 5.8 kLOC of `.c` and `.h` in `src/` at v3.2.0
  (`wc -l`).
- It parses an industrial protocol from the network and serial lines, which
  makes frame parsing a meaningful target for characterization tests and
  fuzzing.
- Its structure has a feature that tests the analysis honestly: transport
  backends (RTU, TCP) are reached through a table of function pointers
  (`struct _modbus_backend` in `src/modbus-private.h`, with members such as
  `recv` and `check_integrity`), so many calls are indirect
  ([FR-015](../specs/requirements.md#fr015-resolve-function-pointer-tables-v1)).
- Licence LGPL-2.1-or-later; obligations in
  [ADR-0003](../adr/0003-licensing.md).

## Module configuration

All library sources are in `src/`, so the default directory-based module
rule would give one module. The libmodbus configuration (B-14) defines:

| Module | Files |
|---|---|
| `core` | `src/modbus.c`, `src/modbus-data.c`, `src/modbus.h`, `src/modbus-private.h`, `src/modbus-version.h` (generated by configure) |
| `rtu` | `src/modbus-rtu*` |
| `tcp` | `src/modbus-tcp*` |
| `tests` | `tests/*` |

## Plan by milestone

### M1: fact database and module map (no LLM)

1. Generate `compile_commands.json` outside the submodule: configure and
   build libmodbus in `build/targets/libmodbus/` under `bear` (B-05). TODO:
   verify that an out-of-tree autotools build works, to keep the submodule's
   working tree clean (`../configure` from a build directory; otherwise copy
   the tree to the build directory first).
2. `lcart analyze` and `lcart map` with the configuration above.
3. Check by hand against the code: `modbus.c` defines
   `_modbus_receive_msg`, `modbus_receive`, `compute_meta_length_after_function`,
   `compute_data_length_after_meta`, `check_confirmation`, `modbus_reply`;
   `modbus-rtu.c` defines `crc16` and `_modbus_rtu_check_integrity`;
   `modbus-tcp.c` defines `_modbus_tcp_check_integrity` (all seen in
   v3.2.0). Calls from `core` into the backends should appear as indirect.
4. Publish the generated module map in the docs (generated file, committed,
   reproduced in CI).

### M2: generated documentation and verification report

1. Generate module descriptions and C4 diagrams for libmodbus with at least
   one local model and, optionally, one remote model (libmodbus is public, so
   `--allow-remote-source` is acceptable here).
2. Publish the docs with their verification reports. Contradicted claims are
   kept and shown: they are the point of the demonstration.
3. Label the real claims and add them to the verifier's labelled set.

### M3: characterization tests of frame handling

Target behaviour (exact functions TODO: verify while writing the tests):

- request parsing on the server side: `modbus_receive` → `_modbus_receive_msg`
  → length computation (`compute_meta_length_after_function`,
  `compute_data_length_after_meta`) → backend integrity check (CRC for RTU,
  MBAP header checks for TCP);
- response handling on the client side: `check_confirmation`;
- `modbus_reply` for each supported function code, including exception
  responses and the length validation added in v3.2.0 (per upstream
  `NEWS.md`).

Seam: feed bytes through a real transport without changing libmodbus, e.g. a
TCP context connected to a socketpair or loopback socket, or an RTU context
on a pseudo-terminal. TODO: verify which works with the public API only.

### M4: fuzzing

- libFuzzer harness that delivers one fuzzed frame per iteration through the
  seam from M3 into the server-side receive path and `modbus_reply` with a
  mapping from `modbus_mapping_new` (TODO: verify signature and teardown
  cost per iteration).
- Built with ASan + UBSan, linking an instrumented build of the unmodified
  libmodbus sources (compiled by our CMake from the submodule's files; no
  changes to them).
- AFL++ optional, once libFuzzer coverage plateaus.
- Findings are reported upstream following its `SECURITY.md`, not fixed
  here.

### M5: modern C++20 wrapper

- Header + small library in `wrappers/modbus-cpp/` (outside the submodule):
  RAII context (`std::unique_ptr` with a custom deleter calling
  `modbus_free`; TODO: verify close/free semantics), `std::span` for
  buffers, `std::chrono` for timeouts, error codes mapped from `errno` /
  `modbus_strerror` into a `Result` type, no exceptions across the C
  boundary.
- Tests: the M3 characterization tests rerun through the wrapper must give
  the same results; plus unit tests of the error mapping.
- Licensing: dynamic linking by default and the other obligations in
  [ADR-0003](../adr/0003-licensing.md#adr0003-lgpl-wrapper-obligations-v1).
