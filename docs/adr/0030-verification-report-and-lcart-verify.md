# 0030. Verification report and `lcart verify`

- **Status:** Accepted (decided by delegation)
- **Date:** 2026-10-18
- **Requirements:** [FR-010](../specs/requirements.md#fr010-verify-claims-v1),
  [FR-011](../specs/requirements.md#fr011-verification-report-v2),
  [NFR-004](../specs/requirements.md#nfr004-deterministic-output-v1),
  [B-28](../plan/backlog.md#b28-verification-report-v1),
  [report format](../specs/claim-schema.md#claim-verification-report-format-v1)
- **Supersedes / superseded by:** — (amends the exit statuses of
  [ADR-0016](0016-facts-export-and-command-line.md#adr0016-exit-status-v1);
  decides how reports spell the evidence that
  [ADR-0029](0029-verdict-evidence-names-its-fact-table.md#adr0029-ids-of-includes-and-calls-v1)
  left to B-28)

## Context

B-28 adds `lcart verify <claims.json> [--db] [--out]`, which verifies a
hand-written claims file with `verify::verify_claim` (B-27) and writes
`verification-report.md` and `verification-report.json`. Open before it:

1. **Exit statuses.** B-28 asks for a new status when a claim is
   contradicted. ADR-0016 has no status for a claims file whose content is
   invalid.
2. **Where the reports go and what may be replaced.** `--out` names lcart's
   output directory for `lcart handoff` (ADR-0028); `map` and
   `query export` replace only their own files (ADR-0017, ADR-0018).
3. **The JSON format**: key order, how evidence is spelled. Verdict
   evidence is a list of `(table, row id)` references (ADR-0029). Row ids
   are per database: they are not in the facts export (ADR-0016) and a
   reader cannot find them in the code.
4. **How files are named.** The fact database stores a file outside the
   analysis root by its absolute path. The facts export names it by the
   spelling of the first directive that includes it; a bundle hides an
   absolute spelling as `<outside-root>/x.h` (ADR-0028). A report ships
   with the documentation (FR-011, B-37), and the verifier still resolves
   only stored paths ([open question](../open-questions.md#open-technical-questions)).
5. **The `VERDICT` table** of the data model, which `lcart verify` could
   fill.

## Options considered

Evidence in the reports:

1. **Row ids with their table** (`call_edge:12`). Exact and short; means
   nothing without the database, and differs between databases of equal
   facts.
2. **The fact itself, with file and line**: per table, the keys a reader
   needs to find it in the code (a call's caller, callee and site, a
   function's file and first line). Longer; independent of row ids.
3. **Both.** Exactness for tools, at the cost of reports that differ
   between equal analyses.

File names:

1. **Stored paths.** What the verifier resolves; absolute paths of files
   outside the root, so a home directory, in a report that is published.
2. **The facts export's names.** No machine-specific prefix for `<stdio.h>`;
   an absolute directive's spelling stays.
3. **The bundle's names** (ADR-0028). What the agent saw, so the names of
   agent output and report agree; no absolute path.

JSON key order:

1. **Sorted**, like the bundle (ADR-0028). The `format` key lands in the
   middle of the file.
2. **Fixed order, `format` first.** lcart can recognise its own report from
   the first two lines before replacing it, as it does for the map and the
   export.

## Decision

<a id="adr0030-command-line-v1"></a>**Command line.** `lcart verify
<claims.json> [--db FILE] [--out DIR]`, with ADR-0016's option syntax.
`--db` defaults to `lcart-out/facts.lcart.db`, `--out` to `lcart-out`; the
reports are `DIR/verification-report.md` and `DIR/verification-report.json`.
The claims file is read up to one byte past the parser's 4 MiB limit and
parsed with `claims::parse_claims`; every claim is verified, then both
targets are checked before either is written: each may be replaced only
if it is absent or is a report of its kind (Markdown: first line
`# Verification report`; JSON: first two lines `{` and
`  "format": "lcart-verification-report",`), and never if it is the fact
database. Each is written to a hidden file and renamed into place,
keeping the permissions of the file it replaces (ADR-0018); the T2 warning
of ADR-0016 covers both. Standard output names both files and the counts
per status. `lcart verify` reads the fact database only: it writes no
`VERDICT` rows (a report is regenerated by running it again), so the
spelling of a `VERDICT` row is left to the command that first writes one.

<a id="adr0030-exit-statuses-v1"></a>**Exit statuses** (amending
ADR-0016): 2 also for a claims file whose content is invalid (the problem
list on standard error, as for lcart.toml); 1 for one that cannot be read;
**6** when the reports are written and at least one claim is
`contradicted`; 0 when none is. No report is written for statuses 1 and 2.

<a id="adr0030-report-format-v1"></a>**Report format.** The JSON report
has the keys of the [report format](../specs/claim-schema.md#claim-verification-report-format-v1)
in that order (`format` `lcart-verification-report`, `format_version` 1
first), every key always present, two-space indentation, `\n` at the end,
and a byte that is not valid UTF-8 replaced by U+FFFD. Claims appear in
the order of the claims file. The Markdown report holds the versions and
the agent, a table of counts per kind and status, the contradicted and
then the unverified claims (confirmed ones are only counted), each with
its statement, text, source, reason and evidence, then the coverage.
Every name, path and claim text in it is a Markdown code span (ADR-0017),
with `|` written `\|` in a table cell, so agent output cannot add
headings, links or HTML or split a cell. Neither format holds a
generation time, so identical input gives identical bytes (NFR-004).
`handoff_contract_version` is `null` and `agent` empty for
`lcart verify`; `lcart ingest` (B-33) fills both. `format_version` changes
with any change to keys, their meaning or their order.

<a id="adr0030-evidence-and-file-names-v1"></a>**Evidence and file
names.** Each piece of evidence is written as the fact it names, with
file and line, never a row id (option 2): the keys per table are in the
report format. Files are named as in a handoff bundle (option 3, file
names): `handoff::file_names_in_bundle`, so no absolute path appears in a
report. The verifier still resolves stored paths only; mapping the
bundle's names back (`<outside-root>/x.h`, `x.h#2`) stays an open question
for B-33.

## Consequences

- The golden reports of the `fn_pointers` fixture are the same on every
  machine with Clang 20; they hold the tool version, so a version bump
  changes them, as it changes the golden bundle.
- A report does not say which database row a verdict rests on; two
  reports of equal analyses are equal. A tool that needs rows can run the
  verifier against the database.
- `report` now depends on `handoff` for the file names; neither links
  `llm`.
- A claim naming a file by its bundle name outside the root
  (`<outside-root>/x.h`) is still `contradicted` / `entity_not_found` under
  complete coverage, although the report would print that name; B-33
  decides the mapping.
- The two reports are replaced one after the other. If the second write
  fails (a full disk), the run exits 1 with the new Markdown report next to
  the earlier JSON one; rerunning `lcart verify` makes them agree again.
- A script that treated any non-zero exit of a future `lcart verify` as a
  crash must accept 6, which means the run succeeded.
