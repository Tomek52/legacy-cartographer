# 0015. lcart.toml is ASCII while toml++ 3.4.0 is in use

- **Status:** Proposed
- **Date:** 2026-10-04
- **Requirements:** [NFR-010](../specs/requirements.md#nfr010-untrusted-input-v1),
  [B-11](../plan/backlog.md#b11-module-rules-v2) criterion 2
- **Supersedes / superseded by:** —

## Context

`lcart.toml` is parsed with toml++
([ADR-0008](0008-configuration-file-format.md)); 3.4.0 is the newest
release, and the version both Ubuntu 24.04 (`libtomlplusplus-dev`) and
Conan Center package. Within seconds, the B-11 fuzz target found two kinds
of undefined behaviour in it on malformed input:

1. **Assertions that become assumptions.** `TOML_ASSERT_ASSUME` is
   `assert()` in debug builds and `__builtin_assume()` under `NDEBUG`
   (`toml++/impl/preprocessor.hpp`). `parse_table_header()` calls
   `parse_key()`, which asserts that the next character starts a key, without
   checking it first: `[=]` aborts a debug build and is undefined behaviour in
   a release build (`toml++/impl/parser.inl`, `parse_key`). The parser has an
   error path for that character right after the assertion.
2. **Unreachable code that is reachable.** `is_non_ascii_horizontal_whitespace()`
   (`toml++/impl/unicode_autogenerated.hpp`) ends in `TOML_UNREACHABLE`
   (`__builtin_unreachable()`) for the code points U+00A1–U+0499 (Latin-1
   Supplement and Latin Extended, so most European letters, plus Greek and
   Cyrillic), U+2C5E–U+2FFF, U+3001–U+3057 and U+FB26–U+FEFE, wherever the
   parser checks for whitespace (computed from the function's bit mask and
   `switch`); U+030C was the fuzzer's input. The macro cannot be redefined
   from outside. toml++'s main branch returns `false` there instead, but its
   version is still 3.4.0 and the fix is listed under "Unreleased" in its
   `CHANGELOG.md` (checked 2026-10-04).

The same "Unreleased" section lowers `TOML_MAX_NESTED_VALUES` from 256 to
128 "to prevent stack overflow on deeply nested arrays/inline tables in
sanitizer builds"; that one is a configuration macro.

Both are reachable from a configuration file that comes with a code base
(NFR-010). Assertions can be switched off from outside (`TOML_ASSERT` is a
configuration macro); the unreachable branch cannot.

## Options considered

1. **Vendor toml++ from its main branch** (one header, MIT). Fixes the
   cause; makes us track an unreleased commit outside Conan and the
   distribution packages ([ADR-0007](0007-cpp23-and-toolchain-baseline.md)),
   and it may have bugs of its own that no release has shaken out.
2. **Another TOML library.** Supersedes ADR-0008 for a bug that upstream has
   already fixed.
3. **Keep toml++ 3.4.0 and keep the triggering input away from it:** turn
   its assertions into no-ops and accept only ASCII text, so no code point at
   or above U+00A0 reaches the whitespace tables. Small and testable.
   Comments and strings in `lcart.toml` cannot use non-ASCII characters
   until it is lifted.

## Decision

<a id="adr0015-ascii-configuration-v1"></a>**`lcart.toml` must be ASCII**
(after an optional UTF-8 byte order mark, which is dropped). The first
non-ASCII byte is a parse error that names its line and column, before
toml++ sees the text. toml++ is included in one file only
(`src/config/src/project_config.cpp`), with `TOML_ASSERT` defined as a
no-op and `NDEBUG` hidden while its header is read, so its assertions are
neither aborts nor assumptions and malformed input reaches its error paths,
and with `TOML_MAX_NESTED_VALUES` at 128 as on toml++'s main branch.

## Consequences

- Module names, paths and comments in `lcart.toml` are ASCII; a file with
  a non-ASCII name can be matched only through wildcards (`*` matches its
  bytes; `?` matches one byte, not one character).
- The fuzz target keeps running in CI, so another such bug in toml++ shows
  up as a red build, not in a user's analysis.
- Revisit when Ubuntu or Conan Center package a toml++ release after 3.4.0:
  check that the whitespace tables no longer end in `TOML_UNREACHABLE` and
  that `parse_key` no longer asserts on reachable input, then supersede this
  ADR.
