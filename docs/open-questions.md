## Questions for the maintainer

1. **Q1. Toolchain of the private code bases.** If they build only with
   MSVC on Windows, the tool must either run on Windows or parse
   MSVC code with Clang on Linux (`clang-cl` mode, Windows SDK headers). This
   changes the toolchain baseline, CI (Windows runner) and the effort of
   ADR-0002. Which is it?
2. **Q2. C++20 or C++23?** GCC 13 and Clang 18 already support
   `std::expected`; moving to C++23 removes `Result<T>` and
   `common::unreachable`. Is C++20 a hard constraint (e.g. to match a work
   toolchain), or a default?
3. **Q3. Configuration file format** (module rules, provider): TOML
   (toml++), YAML (yaml-cpp) or JSON (already a dependency)? JSON adds no
   dependency but is unpleasant to write by hand. Needed by B-11.
4. **Q4. Local model and hardware** for NFR-003: CPU only, or a GPU? This
   decides which model sizes are realistic and whether M2's demo uses a
   local model only.
5. **Q5. Publication.** The repository is private now. Which milestone
   should make it public, and may the libmodbus documentation generated by a
   remote model be published (libmodbus is public, so no confidentiality
   issue, but the provider's terms apply)?
6. **Q6. HTTP client** for providers (M2): libcurl (ubiquitous, C API) or
   cpp-httplib (header-only, needs OpenSSL for HTTPS)?
7. **Q7. Traceability format.** Is the ID + versioned-anchor scheme enough,
   or should requirements map to a formal standard's structure (for example a
   software lifecycle standard used in a regulated domain)?
8. **Q8. Performance target for large code bases** (NFR-005 part 2): what
   size and time budget is realistic for the intended private code base?
